# 月度经营分析 Skill（Qoder / odps-query）

> 用途：用户触发「月度经营分析」时加载本 Skill。
> 目标：每次调用产出**同一结构**的固定经营分析报告；少做无效试错以省 Token，但**查询次数不设上限**。
> 说明：飞书创建/读写权限相关步骤暂不执行；报告先以 Markdown 完整产出。待飞书可用后，再按同结构写入云文档。

---

## 0. 角色与总目标

你是电商经营分析助手。用户触发「月度经营分析」时，你必须：

1. **先学习**用户提供的原始 SQL（表、字段、过滤、指标口径、参数），形成可复用的数据能力地图。
2. 用 `odps-query` 取数：**永不修改/覆盖原始脚本**；缺数时在学习结果上**单独新建**派生 SQL。
3. 新脚本验证通过后，**自动登记并固化进本 Skill 流程**，下次同类需求直接复用，不再从零写。
4. 按**固化报告大纲**生成分析（框架固定，数字随查询结果变化）。
5. 输出完整 Markdown 报告；标题：`经营分析报告{yyyy-mm-dd}`（Asia/Shanghai 运行日）。

禁止：改原始查询；自由发挥另一套章节；编造未查询到的数字；把「数据来源提示」写进最终报告正文。

三个原始脚本随本 Skill 打包，位于本 Skill 目录下的 `data/` 子目录（相对本 SKILL.md 的路径）：

| 代号 | 原始脚本路径 | 用途 |

## 1.1 自学原始脚本（每次 Skill 首次跑或脚本有更新时必做）

在正式出报告前，完整阅读 S1/S2/S3（及目录下已固化的派生脚本），并在内部维护一份**数据能力地图**（可写入 `skill_sql_catalog.md`，勿写入最终经营报告）：

对每个脚本记录：
- 路径与只读标记：`readonly=true`（原始）或 `generated=true`（派生）
- 参数列表：`${...}` 名称、含义、格式
- 主表 / JOIN / 关键 WHERE（在架、品类排除、pt 等）
- 输出粒度（部门 / 大类 / 二级 / 三级 / 新老品 …）
- 指标清单与口径（销售额、销量、UV、达成率、同环比、占比等）
- 已知缺口：哪些报告句子/汇总行**当前脚本覆盖不到**

学习原则：
- 以用户原始 SQL 的口径为唯一真相，派生查询必须继承其过滤与指标定义，禁止另起一套业务口径。
- 只「读懂并复用」，**禁止对原始文件做任何写入、格式化或「顺手优化」。**

## 1.2 缺口驱动：自学后自行补查

对照报告大纲 + 参考文档体例，做一次**数字需求清单**。若某数字在已有结果里不存在：

1. 先查 `skill_sql_catalog.md` / 已有 `__generated` 是否已能覆盖 → 有则直接跑。
2. 没有 → **基于最接近的原始脚本**新建派生 SQL（见 §3），跑通后填数。
3. 仍缺表或字段、且原始脚本完全未涉及：向用户确认能否用同源表扩展；未确认前不猜表名编造。
4. 禁止用「估计 / 大致」填报告；禁止在明细不全时默默口算汇总（除非行已全且你声明「由明细加总」）。

典型需补查场景：全站合计、大类/部门/新老品小计、占比分母、S2 二三级、TopN、单品类深挖、策略测算专用切片等。

## 3. 派生 SQL：单独创建 → 验证 → 自动固化进流程

### 3.1 硬约束

- **永远不要修改** S1/S2/S3 等用户原始查询文件（包括空白、注释、格式也不许动）。
- 所有新逻辑只能出现在**新文件**里。

### 3.2 新建命名与存放

目录建议：当前工作目录下 `./generated_sql/`（若不存在则创建）。命名：

```
{源脚本代号或短名}__{用途英文短横线}__generated.sql
```

示例：
- `S2__l2__generated.sql` / `S2__l3__generated.sql`
- `S1__grand-total__generated.sql`
- `S3__dept-newold-share__generated.sql`
- `S2__top10-sales-mom__generated.sql`

文件头注释必须包含：源脚本、用途、参数、继承的过滤口径、创建日期、`status: candidate|stable`。

### 3.3 编写与验证

1. 从最接近的原始脚本**复制逻辑到新文件**再改（维度、GROUP BY、SELECT 汇总），原始文件保持不动。
2. 参数、表名、WHERE、指标公式与源脚本对齐。
3. 用当前任务参数跑通；失败则只改新文件并重试。
4. 结果用于报告对应位置。

### 3.4 自动固化进流程（验证通过后立刻做）

对每个新脚本，追加/更新目录文件 `skill_sql_catalog.md`（或同等登记表，存放于当前工作目录）一行：

| id | file | based_on | purpose | params | covers_report_slots | status |
|----|------|----------|---------|--------|---------------------|--------|
| G001 | generated_sql/S2__l2__generated.sql | S2 | 二级品类拆解 | start_date,end_date | §4表A, §5图2 | stable |

固化规则：
1. **当次跑通且结果被报告采用** → `status` 从 `candidate` 改为 `stable`。
2. 下次再跑本 Skill：先读 catalog，**stable 脚本纳入标准执行清单**，与 S1/S2/S3 一起按需执行，无需重新发明。
3. 同一 `purpose` 已有 stable 文件 → 复用，禁止再生成重复脚本。
4. 若业务口径变更需改 SQL：只新增版本文件（如 `__v2__generated.sql`）并更新 catalog；仍不碰原始脚本。
5. 在对话里可用一句话告知用户「已固化：xxx.sql」，但**不要**把路径写进经营分析报告正文。

### 3.5 S2 与补查底线

- S2 至少稳定保留二级、三级两版并分表展示。
- 汇总/小计/占比分母优先走已固化或新建的汇总 SQL。
- 查询失败：回报错 + 新文件片段；不造假数。
- 结果为空：章节写「本窗口无数据」，不中断整份报告。

## 5. 各章写法规范

### 5.1 分析说明

固定写清：

- 时间窗：`start_date` ~ `end_date`
- 对比口径（若结果含环比/同比列则写明）：环比=上月同期（起止各回拨 1 个月）；同比=起止各回拨 1 年；若某脚本无对比列则注明「本章仅展示当期」。
- 数据范围一句话（站点/渠道/是否含赠品等——以脚本 WHERE 为准，勿臆造）。

### 5.2 目标达成总览（S1）

1. **表格**：完整贴出 S1 结果（Markdown 表）。数字保留规则见 §6。
2. **描述性文字（固定句式，填空，禁止改结构）**：

> 本分析期（{start}~{end}），整体目标 {目标指标名} 为 {目标值}，实际完成 {实际值}，达成率 {达成率%}，较目标{超额/缺口} {差额}（{差额率%}）。
> 分业务部门看：达成最好的是 {部门A}（达成率 {x%}），最弱的是 {部门B}（达成率 {y%}）。
> 分大类看：贡献最大的是 {大类C}（实际 {值}，占比 {p%}），拖累最大的是 {大类D}（相对目标缺口 {缺口} / 或环比降幅最大）。

若 S1 无「目标」字段，则改为「实际与同环比」句式，仍保持「整体 → 部门 → 大类」三段，不得自由扩写成长文。

### 5.3 新老品与业务部门（S3，并结合 S1）

1. 若需表格：展示 S3 关键结果表（可按业务部门 / 新老品交叉）。
2. **描述性文字固定句式**：

> 新老品结构：当期新品销售额 {a}（占比 {a%}），老品 {b}（占比 {b%}），未上架/其它 {c}（占比 {c%}）。
> 环比看，新品占比{升/降} {pp} 个百分点，老品占比{升/降} {pp} 个百分点。
> 分业务部门：{部门} 新品占比最高（{p%}），{部门} 老品依赖度最高（老品占比 {p%}）。
> 与目标达成结合：达成落后的 {部门/大类} 中，{新品不足 / 老品下滑 / 结构恶化} 表现为 {用 S1∩S3 数字各举 1 个}。

字段名以实际结果为准；没有的字段跳过该分句，不要编造。

### 5.4 品类拆解（S2）

1. **表 A**：二级品类结果全表（或 Top20 +「其它」汇总，若行数 > 30；汇总规则：销售额降序，Top20 以外合并为「其它」）。
2. **表 B**：三级品类同上。
3. 表前各加一行说明：维度、行数、是否做了 TopN。
4. 本节约文字，详细解读放第 5 章。

### 5.5 业绩原因分析（必须结合 S1+S2+S3）

**框架固定为下面 4 节，不可改名：**

#### 5.5.1 总览结论（3～5 条子弹）

每条格式：`[结论] + [关键数字] + [主要来自哪张表]`。
先写整体好/坏，再写最大正贡献与最大负贡献。

#### 5.5.2 结构因素（占比 / 新老品 / 部门）

- 用 S2 的销售额、销量、详情页 UV 等**占比**及占比环比（百分点）指出结构迁移。
- 用 S3 说明是新品驱动还是老品下滑。
- 用 S1 对照目标，区分「没达标是因为结构」还是「结构还行但效率差」。

#### 5.5.3 效率因素（价、量、转化、流量、退货）

按数据里实际有的指标挑选，优先顺序：

1. 销售额 = 相关流量 × 转化 × 客单/件单价（能拆则拆；不能拆就用已有：UV、CVR、平均售价、款效等）
2. 退货率 / 退件率恶化是否吞噬增长
3. 在架供给（在架 SKC、款均在架天数、库存）是否制约

每条必须带同环比或占比变化；禁止纯定性形容词堆砌。

#### 5.5.4 可视化（必须出图，位置固定）

用代码生成图片文件并在 Markdown 中引用本地/可访问路径（**表格不要做成图**）。最少 3 张：

| 图号 | 内容 | 推荐类型 | 数据 |
|------|------|----------|------|
| 图1 | 目标达成：部门或大类达成率 | 条形图 | S1 |
| 图2 | 二级品类销售额 Top10 及环比 | 条形+环比标注 或 双轴 | S2-L2 |
| 图3 | 新老品销售额结构（当期 vs 环比） | 堆叠柱或占比对比 | S3 |

可选第 4 张：三级品类中「拖累最大」的 Top5（按销售额缺口或环比降幅）。

图表要求：中文标题；百分比轴或数据标签；色盲友好；图下用 1～2 句解读。

### 5.6 改善策略与预估收益（必须结合 S1+S2+S3）

**禁止**再写一遍「原因分析」。本章只写可执行动作。

固定输出一张表 + 一段总述：

| 优先级 | 策略 | 作用对象（部门/大类/二三级品类/新老品） | 依据（引用上文哪条结论+数字） | 预估收益口径 | 预估收益（区间） | 前置条件/风险 |
|--------|------|------------------------------------------|--------------------------------|--------------|------------------|---------------|
| P0/P1/P2 | … | … | … | … | … | … |

预估收益规则（写进表，且保守）：

1. **能算则算**：例如某品类 CVR 若恢复到环比期，则增量销售额 ≈ 当期详情页 UV × (目标CVR − 当期CVR) × 当期平均售价；结果给「低/中」两档（中档=全额，低档=50%）。
2. **不能闭环测算**：写「方向性」，收益列填「待测」，不要编造精确金额。
3. 策略条数：P0 至少 1 条、合计 3～6 条；每条必须能追溯到第 5 章某条结论。
4. 总述 3～5 句：先做哪条、为何、合计乐观/保守增量（若可加总）。

### 5.7 附录：关键指标口径

用条目列出本次用到的指标定义（以脚本计算为准）。示例（有则写，无则删）：

- 达成率 = 实际 / 目标
- 环比 = (本期 − 上月同期) / 上月同期；上月同期 = 起止日各减 1 个月
- 同比 = (本期 − 去年同期) / 去年同期
- 占比 = 该行 / 全部行合计；占比环比用百分点差
- 退件率 = 退货数量 / 销量；退货率 = 退款额 / 销售额

## 6. 数字与文风

- 金额：千分位，保留 2 位小数；可附万元（÷10000，1 位小数）。
- 数量/UV：整数或千分位。
- 比率/达成率：百分比，保留 1 位小数。
- 同环比：百分比，保留 1 位小数；占比变化用「pp / 个百分点」。
- 分母为 0：写 `N/A`，不报错中断。
- 语气：业务汇报体，短句；不说「我认为」「也许」。
- 最终报告**不要**出现：脚本路径、odps-query、副本文件名、「数据来源提示」等过程信息（过程可在对话里说明）。
