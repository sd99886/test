# 成衣一部无库存测试款每日推送工作流 — 脱敏说明文档

> 本文档对 n8n 工作流「成衣一部无库存测试推送」的全部节点配置与脚本逻辑做脱敏说明，
> 敏感信息（凭据 ID、token、open_id、真实人名）均已替换为占位符，见文末「脱敏说明」。
> 工作流共 28 个节点，当前已激活，每天 14:00 定时执行。

---

## 一、项目背景与作用

**业务背景**：服装电商独立站每季上新品前，会将部分款式以「无库存测试款」形式少量上架试销（不备货），观察上架后前 3 天的真实销售表现，以此判断款式是否值得追单和正式推广。

**工作流作用**：每天自动完成「取数 → 归档 → 推送」闭环：

1. **取数**：从 MaxCompute 数仓查询当月所有无库存测试款的销售表现（销量、销售额、CTR/CVR/UV 产出等）；
2. **归档**：将全量明细覆盖写入飞书电子表格「推送明细」工作表，作为数据留档；
3. **推送**：给三类人发送飞书交互卡片，**卡片只列出「测试结果=成功」的款**，提醒尽快确认：
   - 每个款式对应的**设计师本人**（只收到自己名下的成功款）
   - 两名**固定推送人**（收到全部成功款汇总）

**测试成功标准**（SQL 内写死）：
上架后第 1 / 2 / 3 天任一天销量 ≥ 5，**或** 前 3 天日均销量 ≥ 15。

### 段 1：鉴权与表格定位（5 个节点）

| # | 节点名 | 节点类型 | 配置说明 |
|---|---|---|---|
| 1 | 获取token | 飞书节点 | `auth → auth:getAccessToken`，用已配置的飞书应用凭据获取 tenant_access_token（后续飞书 API 调用的鉴权基础） |
| 2 | 获取知识库信息 | 飞书节点 | `wiki_spaces → wiki:spaces:node:info`，传入写死的知识库节点 token `<知识库节点token>`，用于定位挂在知识库里的目标电子表格，输出含 `obj_token` |

| 4 | 获取工作表 | 飞书节点 | `spreadsheet → spreadsheet:getSheets`，列出该表格全部工作表，供「解析数据」节点按名称定位「推送明细」表并拿 sheetId / 行数 |

| # | 节点名 | 节点类型 | 配置说明 |
|---|---|---|---|
| 5 | MaxCompute | 自定义节点（CUSTOM.maxcompute） | 挂 MaxCompute 凭据，执行写死在节点里的 SQL（约 3000 字符，详见第五章），输出当月无库存测试款明细，每行一个 SKC |

### 段 3：解析、写入与清理（4 个节点）

| # | 节点名 | 节点类型 | 配置说明 |
|---|---|---|---|
| 6 | 解析数据 | Code 节点 | 核心枢纽脚本（详见第六章 6.1）：把 SQL 结果转成表格 values、定位工作表、计算删行控制字段 |

## 五、MaxCompute 节点 SQL 说明

SQL 分两层：

**1）`daily` CTE（日明细层）**——从商品日明细宽表（`ads_prod_skc_product_info_di`）取数，筛选条件：

| 条件 | 说明 |
|---|---|
| `style_position = '无库存测试款'` | 只取测试款 |
| `pt >= '20251201'` | 分区下限 |
| 首次上架时间 / date_str 均为本月 | 只推「本月新上架 + 本月数据」（SQL 内注释保留了写死测试月 `'2026-09'` 的调试写法） |
| `channels = '独立站'`（nvl 兜底） | 只看独立站渠道 |
| `big_category = '成衣'` 且 `business_group_name = '成衣一部'` | 业务范围 |

并用**窗口函数**（`partition by skc`）在日明细上预计算：

- `d1_sale / d2_sale / d3_sale`：首次上架后第 1 / 2 / 3 天单日销量
- `d1_3_sale`：前 3 天累计销量
- `d1_3_online_days`：前 3 天在架天数（分母用）

**2）外层聚合**——`GROUP BY month_str, skc, 三级类目`，输出 24 列：

| 类别 | 字段 | 逻辑 |
|---|---|---|
| 维度 | month_str, skc, 一/二/三级类目 | 分组键 |
| 属性 | 图片链接, 首次上架时间, 设计师名, 业务部门 | `max()` 去重 |
| 在架状态 | 当月是否在架（decode 1→在架）, 在架天数 | `sum(is_online_adjustment)` |
| 测试表现 | 首次上架后第1/2/3天销量, 前3天日均销 | 窗口值 `max()` + nvl 兜底；日均销 = 前3天销量 ÷ 在架天数（nullif 防除零） |
| **测试结果** | 成功 / 失败 | `d1≥5 或 d2≥5 或 d3≥5 或 日均销≥15 → 成功` |
| 经营指标 | 销售额, 销量 | `sum()` |
| 转化指标 | ctr, cvr, uv产出, 加车率 | 点击/曝光、销量/详情页UV、销售额/UV、加购/UV（均 nullif 防除零） |
| 推送对象 | 固定推送人1, 固定推送人2 | SQL 末尾两个字面量写死（`'<推送人1姓名>'`、`'<推送人2姓名>'`）——保证「只要有数据就一定有推送对象」 |

## 六、各 Code 节点脚本说明（共 11 个，四类逻辑）

### 6.1 解析数据（主枢纽）

- **输入**：MaxCompute 输出的全部行 + 上游「获取工作表 / 获取电子表格信息」的结果
- **输出**：单条 JSON，含 `spreadsheetToken / sheetId / rowCount / valueRows / needClear / clearStartIndex / clearEndIndex / values / rows`
- **逻辑**：
  1. 定义 24 列表头（`header`），与 SQL 输出一一对应；
  2. `get(obj, name)` **大小写不敏感取值**——MaxCompute 返回的英文列名会统一转小写（`CTR→ctr`），该函数按原名→小写两轮匹配，解决字段取空问题；
  3. `toRate / toInt` 数值规整（比率保留 4 位小数、整数转 Number）；
  4. 组装 `values = [header, ...数据行]` 二维数组，供「写入数据」节点整表覆盖写入；
  5. 从「获取工作表」结果中按名称定位「推送明细」表，取 sheetId 和现有行数，计算删行控制字段：`needClear = 现有行数 > 数据行数`、`clearStartIndex/clearEndIndex` 为待删区间；
  6. 同时输出 `rows`（对象数组），供下游三条推送分支消费。
- **注意**：脚本内保留两段注释掉的测试期写死值（设计师名、提前下架列），对应 SQL 已删除「提前下架」列。

### 6.2 按设计师名去重获取姓名（推送入口·设计师）

- **输入**：「解析数据」的 `rows`
- **输出**：每个设计师一条，`{ designerName, alerts(该设计师全部行), skcList, totalCount, spreadsheetToken, sheetName }`
- **逻辑**：按 `设计师名` 字段 trim 后分组（空名跳过），**每人一张卡片、不限条数**（卡片内表格自动翻页）。

### 6.3 解析设计师open_id（搜索结果解析·设计师版）

- **输入**：「按姓名搜设计师」HTTP 响应 + 上游分组数据
- **输出**：`{ ...分组数据, openId, matchedName, receive_id }`，搜不到的返回空（跳过该设计师，不影响其他人）
- **逻辑**（兼容各种姓名结构的关键设计）：
  1. `nameCandidates(emp)` 收集一个员工的全部姓名候选：中文名（`base_info.name` 的 default_value / i18n zh_cn / another_name）、**英文名 `en_name`**、花名 `nickname`；
  2. 三轮匹配：精确相等 → 忽略大小写相等 → 双向包含；
  3. **首个结果兜底**：搜索接口本身就是按姓名查的，姓名结构对不上时直接取第一个结果；
  4. `extractOpenId` 从 `base_info.employee_id`（请求参数已指定 open_id 类型）取值。

### 6.4 组装飞书卡片 / 组装飞书卡片固定推送人1 / 2（三节点同一套代码）

- **输入**：「解析 xx open_id」节点的输出（含 openId + alerts）
- **输出**：`{ receive_id, msg_type: 'interactive', content(卡片JSON字符串), dedupeKey }`，直接对接发卡片节点
- **逻辑**：
  1. 循环处理全部输入项（多人场景每人一张卡）；
  2. **只保留 `测试结果 === '成功'` 的行，无成功款则跳过不发卡**；
  3. 明细表链接：优先 `sheetUrl`，否则取「获取电子表格信息」的 spreadsheet url；
  4. 卡片结构（新模板）：
     - 标题：`无库存测试款推送`（橙色 header，宽屏模式）
     - 正文：`@接收人 您好，这是每日无库存测试款推送明细：[打开明细表](链接)` + `以下skc为测试成功的款，请尽快确认：`
     - 表格（9 列，不限行数，页大小 10）：月 / skc / 首次上架时间 / 图片（`[查看图片](图片链接)` 跳转）/ 设计师名 / 第1天销量 / 第2天销量 / 第3天销量 / 3天日均销
  5. `dedupeKey` 用 open_id 尾 8 位 + 时间戳生成，作为发送 `uuid` 幂等键防重发。

### 6.5 读取固定推送人N字段（推送入口·固定推送人，N=1/2）

- **输入**：「解析数据」的 `rows`
- **输出**：每个推送人一条，`{ personName, alerts, totalCount, spreadsheetToken, sheetName }`
- **逻辑**：按 `固定推送人N` 字段值 trim 后分组（空名跳过），姓名来自 SQL 写死的两个字面量；每人一张卡、不限条数。

### 6.6 解析固定推送人Nopen_id（搜索结果解析·固定推送人版，N=1/2）

- 与 6.3 设计师版**同一套解析逻辑**（姓名候选扩容 + 三轮匹配 + 首结果兜底），差异仅两点：
  - 上游分组节点换成「读取固定推送人N字段」，姓名字段为 `personName`；
  - **搜不到人或接口报错时抛出 Error**（而非静默跳过），错误信息会明确写出搜不到的姓名，提示「只有英文名的请直接填英文名 / 确认在飞书通讯录及应用可见范围内」——便于排查推送失败。

### 6.7 组装飞书卡片批量发送（历史保留）

- **输入**：「按设计师名去重获取姓名」的输出（各设计师分组）
- **输出**：为脚本内 `OPEN_IDS` 数组（写死的 `<固定open_id>` 列表）每人一条卡片消息
- **逻辑**：汇总所有输入项中的成功款并按 `skc+月` 去重，每人生成一张完整的新模板卡片（与 6.4 同模板）。
- **说明**：早期"提前下架批量提醒"方案的历史保留分支，目前与固定推送人 1/2 分支功能重叠，可视情况下线。

## 九、运维注意事项

1. **编辑器旧会话覆盖风险**：工作流曾被 API/CLI 修改后，又被编辑器里打开的旧页面整体保存覆盖（无提示）。**API 改完务必先刷新编辑器再操作**。
2. **PUT API 白名单**：`PUT /api/v1/workflows/{id}` 请求体只允许 `name / nodes / connections / settings` 四个字段，多余字段（如 pinData）会返回 400。
3. **空数据不推送**：SQL 无结果时后续节点无输入，整个推送自然跳过；SQL 末尾写死固定推送人字面量保证「有数据必有推送对象」。
