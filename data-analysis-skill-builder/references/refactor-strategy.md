# 已有技能改造策略指南

> 本文档指导如何将不同来源、不同格式的已有数据分析 skill 改造为 L0-L4 架构。
> 核心原则：**越底层越要统一，越上层越允许差异**。不要求一步到位，优先保障能跑的东西不被改坏。

---

## 一、分层治理原则

L0-L4 各层对"一致性"的要求不同。改造时按以下优先级处理：

| 层 | 改造要求 | 原因 |
|----|---------|------|
| L0 数据层 | **必须补齐** | 表结构是所有分析的基石，缺失则 agent 凭记忆写 SQL → 幻觉 |
| L1 指标层 | **必须补齐** | 口径唯一权威，缺失则同一指标多种算法 → 结果不可信 |
| L2 原子方法 | 尽量标准化 | 通用方法 MTD-01~08 直接复用；无法映射的保留为业务特有方法 |
| L3 场景配置 | 尊重原有实现 | 已验证的 SQL 可直接包装为固化查询，不强求拆解为方法链 |
| L4 决策树 | 渐进引入 | 可先保留原有路由逻辑，后续逐步对齐 5 步路径 |
| 输出层 | 渐进引入 | 可先保留原有输出格式，后续逐步对齐七段式报告 |

> ⚠️ **底线**：L0 + L1 不可妥协。即使其他层全部保留原样，只要补上了表结构和指标口径，改造就有价值。

---

## 二、已有 skill 分类与对应策略

改造前先识别已有 skill 属于哪一类，再选择对应策略。**不要对所有类型套用同一个改造流程。**

### A类：SQL 脚本集

**特征**：每个场景对应一个或多个 SQL 文件，agent 只做调度和拼凑，SQL 本身已验证可靠。

**改造策略**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 补 L0 warehouse_schema.md | 从 SQL 中提取表名、字段、关联关系，用 `DESC` 验证 |
| 2 | 补 L1 metrics_definitions.md | 从 SQL 中反向提取指标公式，与业务方确认口径 |
| 3 | SQL 脚本 → 固化查询 | 每个已验证的 SQL 文件直接包装为 FQ-XX，参数化时间范围和过滤条件 |
| 4 | 补 L3 场景表 | 每个场景一行，固化查询列填 FQ-XX，方法链列可留空或写 "FQ-XX 直连" |
| 5 | L2 暂不强求 | 不强行将完整 SQL 拆解为原子方法，避免丢失隐含的业务逻辑 |
| 6 | L4/输出层可选 | 保留原有路由和输出格式，后续按需对齐 |

**关键提醒**：
- 不要为了"架构整齐"而拆解已验证的 SQL。固化查询的存在意义就是容纳这类"一体化但可靠"的逻辑
- 如果某个 SQL 脚本包含多个分析步骤（如先概览再下钻），可以拆为多个 FQ，也可以保留为一个 FQ——取决于是否需要独立复用其中某一步

### B类：自由文本 prompt

**特征**：无结构化文档，分析逻辑全部写在 prompt 里，靠 agent 的理解力执行。

**改造策略**：这类 skill 本质上没有可复用的工程资产，等同于从零创建。

| 步骤 | 操作 |
|------|------|
| 1 | 将原有 prompt 作为需求参考，走 builder 五步创建工作流 |
| 2 | 从 prompt 中提取业务域、场景列表、指标定义，填入对应模板 |
| 3 | prompt 中的 SQL 示例可作为 L2 伪 SQL 的参考，但需按 8 要素格式重写 |
| 4 | 完整校验后替换原有 prompt |

### C类：半结构化

**特征**：有部分文档（如表说明、指标列表），但格式不统一、不完整，SQL 散落在各处。

**改造策略**：这是最常见的改造对象，需要逐组件判断。

| 组件 | 处理方式 |
|------|---------|
| 已有的表文档 | 对齐到 warehouse_schema.md 格式，补充缺失字段（枚举值、关联键唯一性、更新时效） |
| 已有的指标文档 | 对齐到 metrics_definitions.md 格式，确认口径唯一性 |
| 已验证的 SQL | 包装为固化查询（同 A类策略） |
| 未验证的 SQL / 分析逻辑 | 按 L2 8 要素格式重写为原子方法 |
| 场景路由逻辑 | 映射到 L3 场景表 + L4 决策树 |

### D类：旧版 builder 创建

**改造策略**：直接走 [migration-guide-v1.md](migration-guide-v1.md)。

## 三、探索性需求的处理机制

改造后的 skill 需要同时支持两类需求：

| 需求类型 | 处理机制 | 保障手段 |
|---------|---------|---------|
| **稳定性需求**（高频、已验证） | 固化查询 + L3 场景配置 | SQL 固定、口径锁定、输出可预期 |
| **探索性需求**（临时、发散） | L2 原子方法临时编排 | agent 用 MTD-01~08 现场组合，无需预定义场景 |

**两者的衔接靠沉淀闭环**：

```
用户提出探索性问题
    ↓
L4 "未命中" → L2 方法临时编排 → 执行 → 展示结果
    ↓
用户确认结果有用？
    ├─ 是 → 建议固化为新场景/新 FQ → 下次走稳定轨
    └─ 否 → 仅本次有效，不沉淀
```

**L2 原子方法的覆盖度决定了探索性能力的上限**。MTD-01~08 覆盖了大多数常见分析模式（概览、排行、趋势、对比、环比同比、交叉、枚举探查、漏斗转化）。如果业务域有特殊分析模式（如 DID、四象限、异常检测），应补充为 MTD-09+ 业务特有方法，否则 agent 在探索时会被迫自由写 SQL → 幻觉风险上升。

## 四、改造优先级排序

不要试图一次性完成所有层的改造。按以下优先级分阶段推进：

| 优先级 | 内容 | 价值 | 工作量 |
|--------|------|------|--------|
| P0 | L0 warehouse_schema.md | 消除表结构幻觉 | 小（从已有 SQL/文档提取） |
| P0 | L1 metrics_definitions.md | 消除口径漂移 | 中（需与业务方确认） |
| P1 | 高频场景 → 固化查询 | 锁定已验证 SQL 的稳定性 | 小（参数化即可） |
| P2 | L2 原子方法提取 | 支撑探索性需求 | 中（需拆解和验证） |
| P3 | L3 场景表 + L4 决策树 | 标准化路由 | 小（基于已有路由映射） |
| P4 | 输出层对齐 | 统一报告体验 | 中（需重新设计展示） |

> **最小可用改造 = P0 + P1**。完成这两步后，skill 的知识层已统一、高频路径已锁定，即使其他层保持原样也能安全运行。

---

## 五、改造完成度评估

改造不追求 100% 对齐 builder 模板。以下为各完成度的判定标准：

| 完成度 | 标准 | 是否可用 |
|--------|------|---------|
| 最小可用 | L0 + L1 完整 + 至少 1 个固化查询 | ✅ 可用，知识层统一 |
| 基本达标 | 上述 + L3 场景表覆盖主要场景 + L4 含前置校验 | ✅ 可用，路由标准化 |
| 完全对齐 | 上述 + L2 ≥ 8 个方法 + 输出层七段式 + validate.sh 通过 | ✅ 完整，与新建技能等价 |

**判断原则**：改造的目标是让已有 skill **更安全、更可维护**，而不是让它"看起来像用 builder 创建的"。如果某个改造步骤会破坏已有功能的正确性，那就不要做——保留为固化查询或备注，等条件成熟再处理。
