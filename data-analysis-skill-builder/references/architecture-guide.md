# L0-L4 分层架构编写指南

> 本文档是创建数据分析类 skill 时的参考规范。每层的产物、作用、编写要点与常见陷阱都在这里。

## 架构总览

| 层       | 产物文件                     | 作用                                | 变化频率          |
| ------- | ------------------------ | --------------------------------- | ------------- |
| L0 数据层  | warehouse_schema.md      | 表清单、字段、枚举、关联键、查询前自检               | 低（新增表时更新）     |
| L1 指标层  | metrics_definitions.md   | 指标 ID、公式、口径、陷阱                    | 低（新增指标时更新）    |
| L2 原子方法 | attribution_logic.md §L2 | 可复用的分析模式 + 伪 SQL + 解读规则           | 中（新增方法时追加）    |
| L3 场景配置 | attribution_logic.md §L3 | 场景 ID → 方法链映射                     | 高（新业务场景在此加一行） |
| L4 决策树  | attribution_logic.md §L4 | 用户意图 → 场景路由                       | 中             |
| 输出层     | output_standards.md      | HTML 报告结构 + Chart.js + CSS + 表述铁律 | 低             |
| 主入口     | SKILL.md                 | 工作流、铁律、资源索引                       | 低             |

**设计原则**：稳定的东西沉到底层（表 L0、指标 L1、原子方法 L2），场景（L3）退化为「方法组合 + 参数」配置。新增业务场景时，优先复用 L2 原子方法、只在 L3 加一行配置，不要重复造 SQL。

---

## L0 数据层：warehouse_schema.md

### 编写要点

1. **先探查再写**：用 `DESC <table>`、`SHOW PARTITIONS`、`SELECT DISTINCT ... LIMIT` 探查真实字段和枚举值，不要凭记忆。
2. **表总览表**：每张表标注项目、层（DWD/DWS/ADS/DIM）、粒度、数据规模、是否分区、更新时效（如 T+1/T+0）、用途。
3. **字段说明**：每张表一个表格，列出类型、含义、是否为空。
4. **枚举值**：每个关键分类字段列出真实取值 + 占比（帮助判断主路径 vs 小样本噪声）。
5. **表间关系**：注明关联键、是否唯一、JOIN 是否会膨胀（如 `subsite_comm 是唯一键，JOIN 不膨胀`）。
6. **查询前自检清单**：3-7 条硬检查，构造 SQL 前必过（时间过滤、关联键、NULL 处理、时间语义、全表扫描开关、去重口径、比率分母 NULLIF）。

### 常见陷阱

- **凭记忆填字段类型**：STRING vs BIGINT 搞错 → SQL 类型转换报错或静默错误。
- **漏写枚举值**：后续生成 SQL 时假设了不存在的取值，结果为零。
- **漏写关联键唯一性**：JOIN 后行数膨胀，指标被放大 N 倍。
- **分区表 vs 全量快照表混淆**：分区表用 `pt` 过滤，全量表用业务时间字段 SUBSTR 截取。

## L1 指标层：metrics_definitions.md

### 编写要点

1. **指标速查表**：每个指标一行，含 ID（`M_XXX`）、名称、公式、说明。
2. **按场景分节**：每个场景列出核心维度 + 计算示例 SQL + 专项指标。
3. **口径唯一权威**：同一指标只在此处定义一次，其它文件只引用不重复定义。
4. **常见计算陷阱**：逐条列出（实体 ID 混淆、粒度混淆、NULL 处理、时间语义、比率分母）。

### 常见陷阱

- **同一指标多处定义**：不同文件给出不同公式 → 口径漂移。
- **比率指标分母未用 NULLIF**：分母为零时报错或返回 NULL 被吞掉。
- **分子分母度量不同**：次数/人数/会话数混用（如 CVR 是 order_num / sessions，这是业务既定例外，需特别注明）。
- **漏写"陷阱"节**：后续迭代时同类错误反复出现。

## L2 原子方法：attribution_logic.md §L2

### 编写要点

每个原子方法 = 一个完整的分析单元，包含 8 个结构化要素：

| 要素    | 说明                            |
| ----- | ----------------------------- |
| 触发    | 用户说什么话时应该使用这个方法               |
| 适用表   | 这个方法可以用在哪些表上                  |
| 参数    | 需要传入的变量（时间窗口、维度、指标、过滤条件、阈值等）  |
| 步骤    | 执行的具体步骤                       |
| 伪 SQL | 用 T_ID 别名 + `${参数}` 占位的模板 SQL |
| 输出    | 该方法产出什么                       |
| 陷阱    | 容易出错的地方                       |
| 特别提示  | 业务特有的注意事项                     |

简单方法（如探查枚举）可省略部分要素，但复杂方法必须写全。

### 通用方法库（多数业务域直接可用）

| 方法           | 用途                         |
| ------------ | -------------------------- |
| MTD-01 整体概览  | 取时间窗口内的分布基线，所有分析的起点        |
| MTD-02 排行下钻  | 按维度排行定位 Top/Bottom N，含体量门槛 |
| MTD-03 时间趋势  | 按日/周/月看趋势，发现拐点             |
| MTD-04 前后对比  | 事件前后指标变化，含窗口等长校验           |
| MTD-05 环比/同比 | 短期波动与年度趋势（同比 T−364 对齐星期）   |
| MTD-06 交叉分析  | 两维度交叉发现结构差异                |
| MTD-07 探查枚举  | 字段取值未知时 DISTINCT 探查        |
| MTD-08 漏斗转化率 | 多步骤流程的转化率计算                |

业务特有方法在其后追加（MTD-09+），用同样的 8 要素格式。常见追加类型：分层/四象限、对照组、同比差分 DID、异常预警。

### 常见陷阱

- **方法写死真实表名**：失去通用性，换表时要全局替换。应使用 T_ID 别名。
- **方法粒度太粗**：如只写"看趋势"，没有区分日/周/月，后续场景无法精确匹配。
- **缺陷阱和解读规则**：数据出来了但不知道"好还是坏"，或不知道哪里容易出错。
- **缺触发条件**：agent 不知道什么时候该用这个方法 → 场景匹配不上。

## L3 场景配置：attribution_logic.md §L3

### 编写要点

一张表格，每行一个场景，9 列覆盖完整配置：

| 列     | 说明                                     |
| ----- | -------------------------------------- |
| 场景 ID | 唯一标识                                   |
| 场景名称  | 一句话描述                                  |
| 触发词   | 用户可能说的话（术语 + 口语都要）                     |
| 方法链   | MTD 编号用 `→` 连接，标注每步作用                  |
| 维度    | GROUP BY 的字段                           |
| 指标    | 引用的 L1 指标 ID                           |
| 必需输入  | 该场景启动前必须从用户获取的数据（目标值/文件等），空 = 无需额外输入   |
| 固化查询  | FQ-XX 编号（指向 fixed_queries.md），未固化填 "—" |
| 备注    | 补充说明（如数据上线日期、已知限制、特殊口径约定等），非执行依赖       |

> **为什么没有"关键参数"列？** 参数（时间窗口、过滤条件、阈值、体量门槛等）已在 L2 方法的"参数"要素中定义，agent 执行时根据 L2 定义和用户输入动态绑定。L3 只负责路由配置（什么意图 → 用什么方法链 → 按什么维度/指标展开），避免同一信息在两处维护。

#### "必需输入"列详解

某些场景缺少用户提供的业务数据就无法构造 SQL。"必需输入"列声明这些前置数据，agent 在前置校验阶段检查是否已提供，未提供则主动向用户索取。

**与 L2 参数的区别：**

|    | L2 参数                    | 必需输入             |
| -- | ------------------------ | ---------------- |
| 层级 | 方法级（所有场景共用）              | 场景级（特定场景才需要）     |
| 来源 | agent 从用户问题中提取或按默认值填充    | 必须由用户显式提供        |
| 示例 | `${start_date}`、`${dim}` | 目标换货率阈值、活动商品清单文件 |

**填写格式：** 用简短描述说明需要什么、格式要求。多个输入用分号分隔。例如：

- `目标值: 换货率阈值（百分比数值）`
- `文件: 活动商品清单（Excel/CSV，需含商品编码列）`
- `目标值: GMV 目标（万元）; 文件: 活动SKU清单（Excel，需含商品编码列）`

> ⚠️ 文件类输入只描述**语义**（"商品编码列"），不写死技术列名（如 `sku_code`）。Agent 在实际收到文件时动态识别列名并向用户确认。

**Agent 行为规则：**

1. 命中场景后，检查"必需输入"列是否为空
2. 非空时，逐项检查用户是否已在对话中提供
3. 未提供的项，用业务语言向用户索取（如"请上传活动商品清单文件"）
4. 全部收齐后才进入执行路径选择
5. 收到文件后，按文件输入协议处理（Python 解析 + ODPS 临时表 JOIN），详见下方"文件输入协议"

新增场景用 YAML 模板：

```yaml
场景ID: Sx-y
场景名: <一句话>
触发词: [<口语化表达1>, <口语化表达2>, ...]
方法链: [MTD-xx, MTD-yy]
维度: <group by 字段>
指标: [M_xx, M_yy]
必需输入: <描述需要的数据和格式，空则无需额外输入>
固化查询: ""              # 已验证后填写 FQ-xx，未固化留空
备注: <如：数据从 2026-09-08 上线，仅覆盖新版本>
```

### 常见陷阱

- **场景重复造 SQL**：应该组合 L2 方法，而不是在 L3 里内联写新 SQL。
- **触发词太专业**：只写了术语，没写用户口语说法 → 意图识别漏掉。
- **缺维度和指标列**：agent 执行时不知道按什么分组、用什么指标，只能猜。
- **把必需输入写在备注里**：备注是补充信息，agent 不会主动检查。需要用户提供的数据必须写在"必需输入"列，否则 agent 会跳过索取直接执行 → SQL 缺少关键条件。
- **必需输入没写格式要求**：只写"商品清单"没说需要什么列 → 用户上传了文件但缺少关键字段，agent 无法处理。必须写明文件格式和必需列名。
- **备注写成执行依赖**：备注是补充信息（如数据起始日期），不是 agent 必须等待的前置条件。真正的执行前置应写在"必需输入"列或 L4 决策树的前置校验步骤中。

## L4 决策树：attribution_logic.md §L4

### 编写要点

推荐 5 步线性路径，比简单意图分流更健壮：

```
1. 解析意图
   ├─ 命中 L3 场景？ → 取该场景配置（维度/指标/方法链/固化查询）
   └─ 未命中？ → 用 L2 方法临时编排，并建议沉淀为新场景

2. 前置校验
   ├─ 检查"必需输入"列 → 有未提供的项？向用户索取（目标值/文件等）
   ├─ 涉及枚举/映射未知 → 先跑 MTD-07 探查
   ├─ 时间窗口/切换日未定 → 与用户确认
   ├─ 跨时间点分析？ → 标记需换表
   └─ 查看场景"备注"列 → 注意数据起始日期、覆盖范围等限制

3. 执行路径选择
   ├─ 场景有固化查询（FQ-XX）？
   │   └─ 从 fixed_queries.md 取 SQL → 注入 ${param} → 直接执行 → 跳到第 5 步
   └─ 无固化查询？
       ├─ 选表（L0 选表规则）
       └─ 按方法链顺序执行（L2 步骤 + 伪 SQL）
           └─ 每步校验：窗口等长？体量门槛？度量一致？比率指标分子分母分别聚合后再除？

4. （可选）固化建议
   └─ 方法链执行完毕、结果经确认正确 → 建议将该 SQL 固化到 fixed_queries.md

5. 输出（按方法"输出"定义）
   └─ 结论区分"统计显著"与"业务显著"，小样本不下强结论
```

附带全局 Checklist（方法链执行时每步必过）：

1. 前后/对比窗口等长，避开大促与异常日。
2. 排行/分层先过体量门槛。
3. 比率指标分子分母分别聚合后再除，不可对率值求平均。
4. 数据不足声明：行数 < 10 或窗口 < 7 天时提示。
5. 建议必须可执行：禁止模糊表述，具体到维度和数据。

### 常见陷阱

- **只有 3 层意图分流**：跳过前置校验和选表步骤，导致用错表或枚举值错误。
- **缺全局 Checklist**：方法链执行时没有逐步校验 → 窗口不等长、体量门槛未过等错误漏掉。

## 输出层：output_standards.md

### 编写要点

1. **交付五原则**：数据说明块必备、图表+表格双展示、建议即可执行动作、谨慎询问、自查项单列。
2. **HTML 报告结构**：给出完整骨架（标题 → KPI 卡片 → 数据说明 → 核心诊断 → 数据展示 → 建议 → 自查项 → 固化查询提示（条件显示）→ 免责声明）。
3. **CSS 样式规范**：内嵌样式直接复制使用。
4. **图表选型**：每种分析场景对应一种 Chart.js 图表类型 + JS 配置骨架。
5. **图表选型速查表**：一目了然。
6. **配色方案**：语义化配色（负面=红、正面=绿、警告=橙）。
7. **表述铁律**：禁止 vs 替代对照表。

### 常见陷阱

- **报告数据与查询数据不一致**：在旧报告上改数据，没重新跑查询。必须每次全量重建。
- **时间范围 T-1 算错**：今天是 N 号，"近一周"应为 N-7 ~ N-1，不要写成 N-6 ~ N。
- **Chart.js 数据硬编码**：把上次查询结果写死在 JS 里，下次忘了更新。
- **canvas 与 JS 调用不配对**：HTML 中有 `<canvas>` 但没有对应的 `renderChart()` 调用，或反过来。未输出的图表要同时移除两者。
- **未使用 renderChart() 包装函数**：直接写 `new Chart()` → canvas 不存在时报错。应统一用 `renderChart(canvasId, config)` 包装（canvas 不存在时静默跳过）。
- **分区表与快照表过滤方式混淆**：分区表用 `pt BETWEEN`、快照表用 `SUBSTR(time_field)` 截取，搞混要么报错要么全表扫描。

## 固化查询：fixed_queries.md

### 设计原则

当某个 L3 场景的方法链经过验证、产出的数据正确且符合使用者要求后，可以将完整 SQL **固化**为参数化模板，下次直接执行，避免每次重新组装 SQL 的口径风险。

**核心定位：**

- 固化查询是 L3 场景的**可选优化**，不是必填项。新场景先走方法链编排，验证通过后再固化。
- 固化查询**不替代** L2 原子方法定义。L2 仍是口径权威和方法复用基础。
- 固化查询是"已验证的执行路径快照"，L2 是"可组合的分析能力单元"。两者互补。

**执行优先级：**

```
用户提问 → 命中 L3 场景？
  ├─ 该场景有固化查询（FQ-XX）？ → 注入参数，直接执行固化 SQL
  └─ 无固化查询？ → 按方法链逐步组装 SQL（原有路径）
```

### 编写要点

1. **独立文件管理**：所有固化查询集中在 `resources/fixed_queries.md`，attribution_logic.md 的 L3 场景表中通过 FQ-XX 编号引用。
2. **编号规则**：`FQ-01`、`FQ-02`...，与 L3 场景 ID 不强制一一对应（一个场景可能有多个固化查询，如按月/按周两个版本）。
3. **参数风格**：统一用 `${param_name}` 占位，命名与 L2 方法的参数保持一致（如 `${start_date}`、`${dim_value}`、`${top_n}`）。
4. **必须标注验证信息**：每个固化查询必须注明验证日期和验证人，方便追溯和定期复审。
5. **参数说明表**：列出每个参数的类型、含义、示例值，agent 注入参数时据此校验。参数类型包括：
   - `STRING` / `INT` / `FLOAT`：标量参数，直接注入 SQL
   - `FILE_LIST`：列表型参数，来源于用户上传的文件。详见下方"文件输入协议"

#### 文件输入协议

当固化查询需要用到用户上传文件中的数据（如商品清单、门店列表）时，使用 `FILE_LIST` 参数类型。本协议定义了从文件到 SQL 的完整处理规范。

**L3 "必需输入"列声明格式：**

```
文件: <业务描述>（<文件格式>，需含 <语义描述>）
```

示例：`文件: 活动SKU清单（Excel/CSV，需含商品编码列）`

> ⚠️ **不预定义具体列名**：不同场景下用户上传的文件列名不固定（如 `sku_code`、`商品编码`、`item_id`），因此"必需输入"列只描述**语义**（"商品编码列"），不写死技术列名。Agent 在实际收到文件时动态识别列名。

**固化查询参数说明表中的写法：**

| 参数          | 类型        | 说明               | 示例值            |
| ----------- | --------- | ---------------- | -------------- |
| ${sku_list} | FILE_LIST | 活动SKU清单（语义：商品编码） | 运行时从用户上传文件动态提取 |

> 当固化查询依赖 FILE_LIST 参数时，对应的 L3 场景**必须**在"必需输入"列声明该文件。

**Agent 执行流程（4步）：**

1. **探查文件结构**：用户上传文件后，agent 先用 Python 读取文件的列名和前几行样本，向用户确认哪一列是目标数据列。
   ```python
   import pandas as pd
   # 自动识别文件格式
   if file_path.endswith('.csv'):
       df = pd.read_csv(file_path, nrows=5)
   else:
       df = pd.read_excel(file_path, nrows=5)

   print("文件列名：", list(df.columns))
   print("前3行预览：")
   print(df.head(3))
   ```
   Agent 根据列名和样本内容，智能匹配"必需输入"中声明的语义（如"商品编码列"→ 匹配到 `sku_code` 或 `item_id`），并向用户确认："我识别到 `sku_code` 列是商品编码，是否正确？"
2. **Python 解析提取**：用户确认后，agent 用 Python 提取该列的完整值列表。**解析代码在运行时根据实际文件动态生成，不在技能中预定义。**
   ```python
   # agent 根据步骤1确认的列名动态生成
   target_col = "sku_code"  # 来自步骤1的确认结果
   values = df[target_col].dropna().astype(str).unique().tolist()
   print(f"共提取 {len(values)} 个唯一值")
   ```
   解析后校验：检查提取的值是否为空。若为空，告知用户并中止执行。
3. **动态建表并关联**：agent 根据提取的值列表，**在运行时动态生成**建表和 INSERT 语句，然后通过 odps-query 执行。固化查询 SQL 模板中只写 JOIN 临时表的结构，不写具体的值和建表语句。
   ```sql
   -- 以下由 agent 在运行时动态生成并执行，不在固化查询模板中预定义
   CREATE TEMPORARY TABLE IF NOT EXISTS tmp_s08_sku_list (sku_code STRING);
   INSERT INTO tmp_s08_sku_list VALUES ('SKU001'), ('SKU002'), ...;

   -- 以下是固化查询模板中的固定部分
   SELECT  t.sku_code, SUM(t.gmv) AS total_gmv
   FROM    dwd_order_detail t
   JOIN    tmp_s08_sku_list i ON t.sku_code = i.sku_code
   WHERE   SUBSTR(t.order_date, 1, 10) BETWEEN '${start_date}' AND '${end_date}'
   GROUP BY t.sku_code
   ORDER BY total_gmv DESC;

   -- 查询完成后清理
   DROP TEMPORARY TABLE IF EXISTS tmp_s08_sku_list;
   ```
   **不使用 IN 子句**：IN 超过 1000~2000 个值时可能报错或性能急剧下降，临时表 JOIN 在任何规模下都稳定高效。
4. **异常处理**：
   - 文件无法读取（格式损坏）→ 告知用户，请求重新上传
   - 无法识别目标列 → 列出所有列名，请用户指定
   - 提取值为空 → 告知用户文件中无有效数据，中止执行
   - 临时表创建失败 → 告知用户，尝试分批插入或回退方案
5. **输出解读**：简要说明返回结果的阅读方式（如"关注 pct > 15% 的行"），帮助 agent 正确解读。
6. **SQL 注释头**：SQL 开头注明关联场景 ID 和验证日期，便于排查问题时快速定位。


**注意事项：**

- FILE_LIST 参数的 SQL 模板中**不写死具体的值**，只写 JOIN 临时表的结构框架，agent 在执行时根据 Python 提取的实际值动态生成临时表的 INSERT 语句
- 临时表命名建议加场景前缀避免冲突，如 `tmp_s08_sku_list`
- Python 解析和临时表创建对用户透明，agent 在后台完成，用户只需上传文件即可

### 何时固化

- ✅ 方法链已跑通，结果经业务方确认正确
- ✅ 该场景高频使用（如每周/每日例行分析）
- ✅ SQL 结构稳定，仅时间范围和过滤条件变化
- ❌ 首次创建的场景（应先走方法链验证）
- ❌ SQL 结构仍在调整中
- ❌ 一次性临时分析

### 固化确认流程

> 以下步骤全部由 **agent 内部执行**，对用户完全透明。用户只需回答"是/否"，不需要了解编号、场景 ID 等技术细节。

当方法链执行完毕且结果看起来正确时：

1. **征求用户确认**：将查询返回的数据和初步诊断展示给用户，用业务语言询问："这次分析的结果是否符合预期？如果没问题，我下次可以直接复用这个查询，不用每次重新跑。"
2. **用户确认后提取 SQL**：将本次实际执行的完整 SQL 提取出来，识别其中所有运行时变量（时间范围、维度过滤值、Top N、体量门槛等），替换为 `${param_name}` 占位符。
3. **参数名对齐 L2**：检查每个 `${param_name}` 是否与对应 L2 方法的参数命名一致。不一致则以 L2 为准统一命名。
4. **写入 fixed_queries.md**：从 [templates/fixed\_queries.template.md](../templates/fixed_queries.template.md) 复制模板，agent 自动填入以下内容（用户无需感知）：
   - FQ-XX 编号（agent 按现有编号递增分配）
   - 关联的场景名称和场景 ID（agent 从 L3 场景表中获取）
   - 验证日期（当天）
   - 参数说明表（类型、含义、示例值）
   - 参数化 SQL
   - 输出解读
5. **更新 L3 场景表**：在 attribution_logic.md 的对应场景行的"固化查询"列填入 FQ-XX 编号。
6. **回归验证**：用一组不同的参数值执行固化后的 SQL，确认结果与方法链编排的结果一致。
7. **告知用户**：简要告知"已记住这个查询，下次你说'XX'时我会直接执行"，用用户的语言描述，不提技术术语。

> ⚠️ **禁止跳过第1步**：agent 不能自行判断"结果正确"就自动固化。必须经用户明确确认。这是"人在环路"原则的硬性要求。

### 输出时提示用户

每次生成分析报告时，如果本次使用了固化查询，必须在报告中明确告知用户：

1. **哪些场景使用了固化逻辑**：列出本次用到的固化查询名称和验证日期。
2. **提示可更新**：用业务语言告知用户"如果分析逻辑需要调整，可以让我更新"。

这样用户在每次看到报告时自然了解当前使用的是固化逻辑还是实时编排，并能在业务变化时主动发起更新，无需依赖定时检查机制。

> **原则**：固化查询的维护责任在用户，agent 的职责是每次使用时透明告知、并提供便捷的更新入口。

### 常见陷阱

- **固化了未验证的 SQL**：方法链还没跑通就固化 → 错误被"合法化"。必须先验证再固化。
- **参数名与 L2 不一致**：固化查询用 `${begin_date}`，L2 用 `${start_date}` → agent 注入参数时匹配不上。
- **缺少验证日期**：数仓表结构变更后无法判断固化查询是否过期。必须标注验证日期。
- **固化查询与 L2 口径漂移**：修改了 metrics_definitions.md 中的指标公式，但忘了同步更新固化查询中的 SQL → 同一指标两种算法。修改口径时必须同步检查所有关联的固化查询。
- **硬编码了本应参数化的值**：把具体日期或维度值写死在 SQL 里 → 下次执行时用了旧值。所有运行时变量都必须用 `${param}` 占位。
- **改了底层知识没同步固化查询**：表结构或指标公式变了，固化查询还在用旧逻辑 → 静默产出错误结果。每次修改 L0/L1 后必须检查关联的固化查询。

## SKILL.md 主文件

### 编写要点

1. **frontmatter**：name / description / version。description 写清业务域 + 场景枚举 + 触发词。
2. **核心工作流**：五步，与 L4 决策树一一对应（解析意图 → 前置校验 → 执行路径选择 → 固化建议 → 证据校验）。声明 L4 决策树为执行权威。
3. **数据铁律**：3-7 条硬规则，每条一句话说清「怎么做」+「为什么」。
4. **表速查**：精简表格，完整字段指向 warehouse_schema.md。
5. **资源索引**：指向五个资源文件的链接（含 fixed_queries.md）。
6. **查询执行**：引用 odps-query 技能（非内置脚本）。
7. **输出格式**：七段式结构（含固化查询提示，仅使用固化查询时显示）+ 指向 output_standards.md。
8. **严格约束**：禁止幻觉、拒绝模糊、人在环路、格式强制、探查优先、查询前自检。
